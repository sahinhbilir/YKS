# Connected, but the teacher notebook is missing

The Settings `bulutBaglan` handler signed in, reserved local student slots, then immediately uploaded the local notebook. It never called the full-notebook download used by initial teacher setup. Connecting an empty device could therefore replace both the latest backup and that day's snapshot. The previous Google authorization fix did not fix this separate data-loading bug.

## Corrected behavior

- Connecting now reads the latest notebook from the server and offers to restore it, showing the account, date, student count and result count. Settings also has **Buluttaki defteri aç** for an existing session. Neither action uploads the local notebook as the latest cloud copy. Student slot reservation remains in package export and account publishing.
- An existing local teacher notebook is preserved in a separate immutable restore point before it is replaced. Failed local persistence is not reported as successful restoration. Initial setup uses the same download flow and directs failed retries to Settings, without suggesting a data reset.
- Automatic backup pauses during connection/restoration. Backups use a Firestore transaction to compare the current cloud copy against this device's last acknowledged SHA-256 fingerprint. The fingerprint is saved per account for subsequent page loads; another tab cannot advance an already-open tab's baseline. Unknown or changed cloud data stops the upload. An empty roster or results list cannot automatically replace a populated one.
- On first use after this update, an existing cloud copy may need review before automatic uploads resume. Open the cloud notebook, or explicitly choose **Defteri buluta yedekle** to upload the local copy. A confirmed replacement archives the previous cloud copy in the same transaction. An archive failure or a changed remote copy prevents replacement. A completely empty local notebook cannot create a new backup.
- Daily snapshots remain available under **Bulut yedek geçmişini göster**. If an automatic backup pauses after a history restore, **Defteri buluta yedekle** offers the protected upload of that restored state.

## Recovery on the affected device

1. Refresh the site and open **Ayarlar → Buluttaki defteri aç**. Use the Google account that held the notebook.
2. Inspect the counts before accepting the restoration.
3. If the latest copy is empty or missing, open **Bulut yedek geçmişini göster**. Look for a populated daily backup or restore point and restore it. Today's daily copy may have been replaced by the old connection handler; earlier days and immutable restore points are separate documents.
4. If there is no suitable cloud copy, keep the original device/browser intact. Its local notebook or an exported JSON backup may still contain the data. **Buluttan sonuçları çek** only imports results for an already-known roster; it does not restore a teacher notebook.

The repository tests reproduce the missing-download and overwrite paths. Fifteen new application cases cover restoration, cancellation, empty/missing/corrupt backups, pending sign-in, local persistence failure, protected replacement, account isolation, reloads, other-device updates, populated daily history behind an empty latest copy, and local edits during restoration. Emulator tests check the combined archive/replacement transaction and rollback on archive denial. Firebase behavior follows the documented [transaction guarantees](https://firebase.google.com/docs/firestore/manage-data/transactions) and [server reads](https://firebase.google.com/docs/firestore/query-data/get-data).

No private production cloud data was accessible during this repair. The fix does not establish which historical copies exist and cannot recreate data absent from all cloud, local and exported backups. Older tabs still running the previous code should be refreshed. This is conflict detection and explicit restoration, not automatic merging of two edited teacher notebooks.

## The cloud copy is compressed (`gz1:`)

The teacher notebook is one string, `veri`, in `ogretmenYedek/{uid}`, and Firestore rules cap that string at 900 000 characters (a Firestore document is 1 MiB). With Sıralamalar, Etütler, Yoklama, Türkiye geneli, Konu Takibi, Etüt planı and the students all in one notebook, a real school reached **"Defterin bulut yedeği sınırı doldu."** while saving Konu Takibi reports.

- **Format.** `veri` is now `'gz1:' + base64(gzip(UTF-8 JSON))`, written with the browser's `CompressionStream('gzip')` (`bulutVeriKodla`) and read with `DecompressionStream` (`bulutVeriCoz`). A copy that does not start with `gz1:` is the old plain JSON and is read as before. If the browser has no `CompressionStream` (or compression fails), the notebook is written as plain JSON exactly as it used to be. Every encoded string is decoded again before it is written; a copy that does not come back byte for byte is not written compressed.
- **Same document, same rules.** The main copy, the daily copies (`gecmis/{gün}`), the restore points (`geriNoktalari/{id}`, including the day-start and pre-rollback protection copies), the rollback in `bulutSurumuneDon`, and the test-account notebook (`testDefter/{uid}`) all store the encoded string. `boyut` is the stored length. `firestore.rules` is unchanged: the encoded string is still a string of at most 900 000 characters. Old daily copies stay plain and still restore.
- **Comparisons use the decoded JSON.** The conflict check inside the backup transaction, the confirmed-overwrite check, the last-acknowledged SHA-256 baseline, the lock follower and the viewer's snapshot comparison, the logout verification and the rollback selection all compare decoded JSON. A plain copy and a `gz1:` copy of the same notebook are the same notebook. Baselines remain hashes of the JSON.
- **A copy that cannot be decoded is never treated as empty or overwritten.** Decoding throws (a corrupt `gz1:` string, or a browser without `DecompressionStream`); the backup transaction aborts with "Buluttaki defter doğrulanamadı; üzerine yazılmadı", the readers report an error, and logout stops without clearing the device. Restoring still needs the existing confirmation.
- **Size limits.** The cloud limit (900 000) applies to the **stored** string. The in-app whole-notebook guard used by the Sıralamalar, Etütler, Yoklama, Türkiye geneli, Etüt planı and Konu Takibi writers and by bulk student import is now `DEFTER_HAM_UST_SINIR` = 2 500 000 bytes of JSON (it protects device storage); each page keeps its own smaller cap. Student packet and `denemeOkul` limits are a different channel and did not change.
- **Ayarlar → Genel → Defter boyutu** lists what fills the notebook (Sıralamalar, Etütler, Yoklama, Türkiye geneli, Konu Takibi, Etüt planı, Öğrenciler, Diğer; 1 KB = 1000 bytes), the total against the 2 500 KB limit, and **Bulutta: N KB / 900 KB**, the stored size of the last successful save in this session ("—" before the first save). The limit errors point to it.
- **Rollout.** A tab opened before the update cannot read a `gz1:` document and must be refreshed; ask both teachers (owner and co-teacher) to refresh before their next save. The first save after the update rewrites the main copy as `gz1:`. On synthetic notebooks of repeated realistic rows with random numbers, gzip plus base64 stores about 26% of the JSON size (about 3.9x smaller); real notebooks repeat more and should do at least as well.
